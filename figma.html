Parallel design work without breaking what's in build

Two designers, two tickets, one product surface. This is how the work stays isolated, how it gets back into the main file, and what stops an in‑flight change from quietly moving a screen a developer is already building.

Start here

Branching and versioning are not the same thing

This is the distinction everything else depends on, and the one teams most often collapse. You need both. They solve different problems.

Backward looking

Version history

A timeline of one file. Figma autosaves checkpoints and you can name specific ones, for example MYLO-412 handoff.

It is linear. You can view, restore, or link to a past state, but you cannot work inside one. Its job is proof and recovery: what did this file look like on the day we agreed it.

Every file, every paid plan.

Forward looking

Branching

A parallel copy of a file that you work in, then merge back into the main file.

It is concurrent. Two designers can hold separate branches off the same main file at once, and the merge step forces someone to resolve the conflicts between them. Its job is isolation: keeping unfinished work away from the file developers build from.

Organization and Enterprise plans, Full seat.

The git comparison is close enough to be useful. Version history is roughly the commit log, branching is roughly branches. Where it breaks: Figma's history is mostly time‑based autosave rather than deliberate commits, and you cannot diff or roll back a single frame. Restore is all or nothing, at file level.

Non-negotiable

The five rules

Figma gives you isolation. It does not give you discipline. Everything below is convention, and the process fails without it.

Rule 01 One main file per surface

Not one per company. "Pensions Dashboard / Main", "Onboarding / Main", each with its own branches and its own merge cadence. A single shared main file across the whole product recreates the problem you are solving.

Rule 02 Nobody edits main directly

Main changes by merge, never by hand. One named reviewer per merge, and a fixed weekly merge window rather than merge‑whenever.

Rule 03 One branch per ticket, named with the key

Short‑lived, and pull from main often. You cannot cherry‑pick which main‑file changes to take, so the longer a branch runs the worse the conflict resolution gets.

Rule 04 · highest risk Two branches on the same screens is the danger zone

Avoid it where you can. Where you cannot, sequence the merges deliberately, and have the second branch pull from main before it merges. This is where silent overwrites happen.

Rule 05 · highest risk Never edit a delivered screen in place

Branch it and raise a new ticket instead, so the change is visible, reviewable and traceable to a decision. Silent edits to screens already in build are the single most common failure.

Rule 06 Ready for dev lives in main, tickets carry a pinned link

Never set the status inside a branch. And a normal file link is live: it shows today's file, not March's. Add the version‑history link so the ticket keeps the design that was actually signed off.

What you give up

Versioning does not substitute for branching. It is a different capability that happens to sit next to the same problem.

Gap 01 Recovery, not prevention

If two initiatives touch the same screens, nothing warns you and nothing asks you to resolve it. You will find out afterwards, and restore from a named version. The damage happens either way.

Gap 02 Restore is whole-file

You cannot roll back a single frame. Restoring main to recover one screen also throws away everything else that landed after that point, including other people's work.

Gap 03 No review step

There is no side‑by‑side comparison of what changed. Review has to happen as a meeting or a comment thread, before the paste‑back rather than as part of it.

Practice 01 Name a version either side of every paste-back

before MYLO-412 paste and after MYLO-412 paste. Two named points is what makes the difference identifiable later, and gives you a clean restore target.

Practice 02 Named owner and a fixed cadence per working file

One person is responsible for getting each working file back into main, on a schedule. Without that, working files become permanent forks and main slowly stops being the truth.

Practice 03 Everything else from approach A still applies

One main file per surface. Ready for dev only in main. Pinned version link on every ticket. Never edit a delivered screen in place. The rules do not change, only the enforcement.

The honest read: beyond two parallel initiatives on the same surface, this stops scaling. That is the strongest practical argument for moving to the Organization tier, and it is worth costing that against the hours lost to reconciling overwrites.

Wiring it to Jira

Beyond installing the Figma for Jira app, four things are worth setting up.

WhatWhy it earns its place
File link on the issueRegisters file‑level webhooks automatically, with no team URL or admin configuration. The issue then reflects design updates and Dev Mode status, and ready for dev in Jira mirrors the status in Figma.
Status automationTransition the issue, apply labels and notify developers when the design status flips. Removes a whole class of manual chasing.
JQL filterFind issues in To do with a linked design marked ready for dev. This becomes the sprint‑planning view of what is genuinely ready to pick up.
Dev resourcesLink the ticket, the repo and Storybook to the frame itself in Dev Mode. Added to a component, they propagate to every instance.
