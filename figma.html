Four rules that hold it together

The tool gives you isolation. It does not give you discipline. These are the conventions the process needs to survive a busy sprint.

Rule 01 Nobody edits main directly

Main is changed by merge, never by hand. One named reviewer per merge, and a fixed weekly merge window rather than merge‑whenever.

Rule 02 One branch per ticket

Name it with the issue key. Keep it short‑lived and pull from main often, because you cannot cherry‑pick which main changes to take.

Rule 03 Ready for dev lives in main

Never set the status inside a branch. Developers build from main only, so a status anywhere else is a false signal.

Rule 04 Tickets carry a pinned link

A normal file link is live and shows today's file. Add the version‑history link so the ticket keeps the design that was actually signed off.

Wiring it to Jira

Beyond installing the app, four things are worth setting up.

WhatWhy it earns its place
File link on the issueRegisters file‑level webhooks automatically. No team URL or admin config needed. The issue then shows design updates and Dev Mode status.
Status automationTransition the issue and notify developers when the design status flips. Removes a whole class of manual chasing.
JQL filterFind issues in To do with a linked design marked ready for dev. This becomes the sprint‑planning view of what is genuinely ready.
Dev resourcesLink the ticket, the repo and Storybook to the frame itself in Dev Mode. Added to a component, they propagate to every instance.
